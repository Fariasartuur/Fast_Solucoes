4. Padrão de erros

Erros de regra de negócio são lançados como ServicoItemError(statusCode, message) (definido em database_servico_item.js e reutilizado nos demais arquivos). O Fastify usa a propriedade statusCode do erro para responder automaticamente:

HTTP/1.1 409 Conflict
{ "statusCode": 409, "error": "Conflict",
  "message": "Estoque insuficiente de \"Correia\": disponível 1, necessário 2." }

O frontend sempre exibe o campo message. Por isso as mensagens são escritas em português e já explicam o problema ao usuário.

CódigoQuando
400Dado inválido: quantidade não inteira/≤ 0, data inexistente ou em formato errado, status inválido, preço negativo, CPF/CNPJ com dígitos errados, e-mail inválido, texto longo demais, pagamento com data futura ou anterior ao serviço.
404Serviço, peça ou vínculo peça–serviço inexistente.
409Conflito com o estado atual: estoque insuficiente; exclusão de peça já usada em serviço.

5. Referência da API

Serviços

RotaDescrição
GET /servico ALTERADALista os serviços com os campos calculados custo_pecas e lucro, além de status e data_pagamento. Aceita ?search= (contratante ou tipo).
GET /servico/:id NOVAUm serviço, com os mesmos campos da listagem. 404 se não existir.
POST /servico ALTERADACria o serviço. Opcionais: pecas, status, data_pagamento. Responde 201 com { "id_registro_servico": 21 }.
PUT /servico/:id ALTERADAEdita contratante, data, valor e tipo. Não altera o pagamento. 404 se não existir; 400 se a nova data for posterior à data em que o serviço foi pago.
PUT /servico/:id/pagamento NOVAMarca como pago ou desfaz (seção 7).
DELETE /servico/:id ALTERADADevolve todas as peças ao estoque e exclui o serviço, na mesma transação.

Exemplo: cadastrar serviço com peças, já pago

POST /servico
{
  "contratante": "Academia Corpo em Forma",
  "data": "2026-11-18",
  "valor": 350,
  "tipo": "Manutenção corretiva da esteira",
  "pecas": [ { "id_item": 16, "quantidade": 1 }, { "id_item": 17, "quantidade": 2 } ],
  "status": "Pago",                 // opcional (padrão "Pendente")
  "data_pagamento": "2026-11-20"    // opcional (padrão: hoje, se Pago)
}
→ 201 { "id_registro_servico": 18 }
→ 409 se faltar estoque de qualquer peça (nada é gravado, nem o serviço)

Exemplo: item da listagem

{ "id_registro_servico": 21, "contratante": "SmartFat", "data": "2026-11-20T03:00:00.000Z",
  "valor": "650.00", "tipo": "Manutenção", "status": "Pendente", "data_pagamento": null,
  "custo_pecas": "142.00", "lucro": "508.00" }
Valores DECIMAL chegam como texto ("650.00") pelo driver mysql2, e datas DATE chegam como "AAAA-MM-DDT03:00:00.000Z". O frontend converte nos dois casos.

Peças do serviço

RotaDescrição

POST /servico/:id/pecasCorpo { "id_item": 16, "quantidade": 2 }. Adiciona a peça (ou soma à quantidade, se já estiver no serviço) e baixa o estoque. 201.

Itens (peças)

RotaAlteração

6. Peças e estoque (transações)

Toda operação que mexe em peças de serviço é executada por withTransaction(fn): abre uma conexão do pool, faz BEGIN, executa e faz COMMIT; em qualquer erro faz ROLLBACK (nada é gravado pela metade) e sempre libera a conexão. As linhas envolvidas são bloqueadas com SELECT ... FOR UPDATE para evitar inconsistência em operações simultâneas.

FunçãoRegra
adicionarPecaTrava serviço, peça e vínculo. Baixa o estoque e insere o vínculo, copiando preco_custo (ou 0) para custo_unitario. Se a peça já está no serviço, apenas soma a quantidade (o custo do primeiro registro é mantido).
retirarEstoqueSaldo disponível = soma de todos os registros de tb_estoque da peça. Se insuficiente → 409. A baixa começa pelo registro mais antigo.
devolverEstoqueSoma ao registro mais antigo da peça. Se a peça não tiver mais registro de estoque, cria um novo.
setQuantidadeDiferença positiva → retira; negativa → devolve.
devolverTodasPecasUsada antes de excluir um serviço; as linhas de tb_servico_item saem pelo ON DELETE CASCADE.
Por que o custo é copiado? O lucro de um serviço precisa refletir quanto a peça custou quando foi usada. Se o técnico comprar a mesma peça mais cara depois, os serviços antigos não mudam.

O lucro não é armazenado: GET /servico calcula custo_pecas = SUM(quantidade × custo_unitario) e lucro = valor − custo_pecas com LEFT JOIN (serviços sem peças têm custo 0).

7. Regras de pagamento

Implementadas em pagamento.js e usadas em servico.js:

PUT /servico/21/pagamento
{ "status": "Pago", "data_pagamento": "2026-11-20" }   // data opcional: padrão = hoje
→ 200 { "id_registro_servico": 21, "status": "Pago", "data_pagamento": "2026-11-20" }

PUT /servico/21/pagamento
{ "status": "Pendente" }                              // desfaz e limpa a data
→ 200 { "id_registro_servico": 21, "status": "Pendente", "data_pagamento": null }
  • status aceita apenas "Pago" ou "Pendente" (maiúsculas/minúsculas ignoradas e normalizadas).
  • data_pagamento não pode ser futura nem anterior à data do serviço. Com "Pendente", qualquer data enviada é ignorada.
  • parseData exige AAAA-MM-DD de uma data real (rejeita 2026-02-30). Aceita também o formato ISO devolvido pelo próprio banco, usando só os 10 primeiros caracteres.
  • A comparação de datas é feita como texto AAAA-MM-DD (DATE_FORMAT no SQL), evitando problemas de fuso horário.
  • O banco reforça a coerência com a restrição chk_servico_pagamento (Pago ⇔ possui data).

8. Dados do prestador

  • A tabela tb_prestador tem uma linha só (id_prestador = 1). O PUT usa INSERT ... ON DUPLICATE KEY UPDATE, criando na primeira vez e atualizando nas seguintes.
  • Todos os campos são opcionais; textos vazios são gravados como null e espaços extras são removidos.
  • CPF/CNPJ é aceito com ou sem pontuação e gravado só com dígitos (11 ou 14); outro tamanho → 400.
  • E-mail validado por formato; tamanhos máximos: nome, e-mail, cidade e chave PIX com 100 caracteres, telefone com 20.
  • exibir_nos_documentos: só fica falso se for enviado false explicitamente.

10. Pontos de atenção

  • Reinicie o backend após atualizar o código: o Node não recarrega arquivos alterados automaticamente.
  • Migrações fora do Git: o .gitignore ignora *.sql. Adicione !backend/migrations/*.sql para versioná-las.
  • registro_itens.js (não alterado): usa app.db_registro_item, mas o servidor registra db_registro, então a rota falha ao ser chamada. Ela também não recebe id_item.
  • Nome do erro: ServicoItemError surgiu nas regras de peças e passou a ser usado para todos os erros de negócio. Se o grupo preferir, pode ser renomeado (ex.: ApiError) em uma refatoração futura.
  • .env: o arquivo backend/.env com as credenciais do banco não vai para o Git. Cada integrante precisa criar o seu.
