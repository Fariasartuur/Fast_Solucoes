Documentação das Alterações do Banco de Dados

Sistema Fast Soluções · Banco inovatec (MySQL 8.4) · Documento complementar a Documentacao_Banco_de_Dados.pdf

Este documento registra, de forma cumulativa, todas as alterações estruturais feitas no banco de dados do sistema Fast Soluções durante a implementação das novas funcionalidades. O sistema é usado por um técnico autônomo que conserta equipamentos de academias de terceiros: ele compra peças, usa essas peças nos consertos e cobra pelo serviço. As alterações descritas aqui permitem relacionar as peças compradas aos serviços prestados, controlando estoque e lucro real de cada atendimento, registrar se cada serviço já foi pago pela academia (contas a receber) e guardar os dados do técnico usados nos recibos e orçamentos.

A estrutura original (tabelas, campos e relacionamentos) continua descrita no documento Documentacao_Banco_de_Dados.pdf. Aqui são detalhados apenas os elementos novos ou alterados.

3. Etapa 1.1 — Peças Usadas no Serviço

Objetivo: permitir que, ao registrar um serviço, o técnico informe quais peças do seu estoque foram usadas. Com isso o sistema consegue descontar o estoque automaticamente e calcular o lucro real de cada serviço (valor cobrado menos o custo das peças).

tb_itemALTERADA

Catálogo de peças compradas pelo técnico. Recebeu uma nova coluna para o custo de aquisição.

  • preco_custo DECIMAL(18,2) NULL: Preço pago por uma unidade da peça. É opcional (aceita nulo) para não obrigar o preenchimento em peças já cadastradas; nesse caso o custo é considerado R$ 0,00 nos cálculos.
  • Restrição chk_item_preco_custo: impede valores negativos (preco_custo IS NULL OR preco_custo >= 0).
tb_servico_itemNOVA

Tabela associativa que resolve o relacionamento muitos-para-muitos entre serviços e peças: um serviço pode usar várias peças, e uma mesma peça pode ser usada em vários serviços. Cada linha representa "a peça X foi usada N vezes no serviço Y".

  • id_servico_item (PK) INT: Identificador único do registro (Auto Incremento).
  • id_registro_servico (FK) INT NOT NULL: Serviço em que a peça foi usada. Referencia tb_registro_servico (Deleção/Atualização em cascata).
  • id_item (FK) INT NOT NULL: Peça utilizada. Referencia tb_item (Deleção restrita; atualização em cascata).
  • quantidade INT NOT NULL: Quantas unidades da peça foram usadas. Deve ser maior que zero.
  • custo_unitario DECIMAL(18,2) NOT NULL DEFAULT 0.00: Cópia do preco_custo da peça no momento em que foi usada. Assim, se o técnico comprar a mesma peça mais cara no futuro, o lucro dos serviços antigos não muda.

Restrições

  • uk_servico_item (UNIQUE em id_registro_servico, id_item): a mesma peça aparece no máximo uma vez por serviço; para usar mais unidades, aumenta-se a quantidade.
  • chk_si_quantidade: quantidade > 0.
  • chk_si_custo: custo_unitario >= 0.

4. Relacionamentos e Integridade

Relacionamentos introduzidos nesta etapa, somados aos já existentes:

  • Serviço → Peças usadas (1:N): tb_servico_item depende de tb_registro_servico. Se um serviço for excluído, as peças vinculadas a ele são removidas automaticamente (ON DELETE CASCADE). A devolução das quantidades ao estoque é feita pelo backend (Etapa 1.3) antes da exclusão.
  • Peça → Usos em serviços (1:N): tb_servico_item depende de tb_item. Uma peça que já foi usada em algum serviço não pode ser excluída (ON DELETE RESTRICT), preservando o histórico de custos e o cálculo de lucro dos serviços.
  • Com isso, tb_registro_servico deixa de ser uma tabela isolada e passa a se relacionar com tb_item por meio de tb_servico_item (relacionamento N:N).
  • Os relacionamentos originais (tb_estoque e tb_registro_item com tb_item) permanecem inalterados.
Observação: o desconto e a devolução de estoque (tb_estoque.quantidade) não são feitos por triggers no banco, e sim pelo backend, dentro de uma transação. Essa lógica está descrita na seção 5.

5. Regras de Movimentação de Estoque (Etapa 1.3)

A Etapa 1.3 não alterou a estrutura do banco. Ela implementou, no backend, as regras que mantêm tb_estoque e tb_servico_item consistentes entre si. Toda operação é executada em uma transação (BEGIN / COMMIT / ROLLBACK), com as linhas envolvidas bloqueadas por SELECT ... FOR UPDATE: se qualquer passo falhar, nada é gravado.

Operação (rota)Efeito em tb_servico_itemEfeito em tb_estoque
Adicionar peça ao serviço
POST /servico/:id/pecas		Insere a linha copiando tb_item.preco_custo (ou 0) para custo_unitario. Se a peça já estiver no serviço, apenas soma a quantidade.Subtrai a quantidade. Se a peça tiver mais de um registro de estoque, o saldo é a soma deles e a baixa começa pelo mais antigo.
Alterar quantidade
PUT /servico/:id/pecas/:idItem		Atualiza quantidade.Aumento: subtrai a diferença. Redução: devolve a diferença.
Remover peça do serviço
DELETE /servico/:id/pecas/:idItem		Exclui a linha.Devolve a quantidade usada.
Cadastrar serviço com peças
POST /servico (campo pecas)		Insere o serviço e todas as peças na mesma transação.Subtrai a quantidade de cada peça.
Excluir serviço
DELETE /servico/:id		Linhas removidas pelo ON DELETE CASCADE.Devolve todas as peças antes da exclusão.

Validações

  • Estoque insuficiente (HTTP 409): a operação é recusada e nada é gravado. Ex.: Estoque insuficiente de "Correia": disponível 1, necessário 2. No cadastro de serviço com peças, nem o serviço é criado.
  • Quantidade inválida (HTTP 400): deve ser um número inteiro maior que zero.
  • Serviço ou peça inexistente (HTTP 404).
  • Exclusão de peça já usada em serviço (HTTP 409): bloqueada pela FK fk_si_item (ON DELETE RESTRICT), com mensagem explicativa ao usuário.
  • Devolução sem registro de estoque: se o registro de estoque da peça tiver sido apagado, a devolução cria um novo registro com a quantidade devolvida.

6. Cálculo do Lucro por Serviço (Etapa 1.5)

A estrutura permite calcular, diretamente no banco, o custo das peças e o lucro de cada serviço. A partir da Etapa 1.5, essa consulta é usada pela rota GET /servico, que passa a devolver os campos calculados custo_pecas e lucro (não armazenados; calculados a cada consulta). O LEFT JOIN garante que serviços sem peças também apareçam, com custo R$ 0,00 e lucro igual ao valor cobrado.

SELECT s.id_registro_servico,
       s.contratante,
       s.valor                                              AS valor_cobrado,
       COALESCE(SUM(si.quantidade * si.custo_unitario), 0)  AS custo_pecas,
       s.valor - COALESCE(SUM(si.quantidade * si.custo_unitario), 0) AS lucro
  FROM tb_registro_servico s
  LEFT JOIN tb_servico_item si ON si.id_registro_servico = s.id_registro_servico
 GROUP BY s.id_registro_servico;

7. Etapa 2.1 — Contas a Receber

Objetivo: registrar se cada serviço já foi pago pela academia e em que data. É comum o técnico fazer o conserto e receber dias depois; sem esse controle ele não sabe quanto tem a receber nem quem está devendo. Com os novos campos, o sistema consegue listar os serviços pendentes, somar o valor em aberto e calcular há quantos dias cada um está sem pagamento.

tb_registro_servicoALTERADA

Registro dos serviços prestados às academias. Recebeu duas colunas para o controle de pagamento.

  • status VARCHAR(10) NOT NULL DEFAULT 'Pendente': Situação do pagamento do serviço. Aceita somente 'Pago' ou 'Pendente'. Todo serviço novo começa como 'Pendente', assim como os serviços que já existiam no momento da migração.
  • data_pagamento DATE NULL: Data em que o técnico recebeu o pagamento. Preenchida apenas quando o serviço está pago.

Restrições

  • chk_servico_status: status IN ('Pago', 'Pendente'), impedindo valores digitados de forma diferente (ex.: "pago", "Paga", "Sim").
  • chk_servico_pagamento: garante a coerência entre os dois campos. Um serviço 'Pago' exige data_pagamento, e um serviço 'Pendente' não pode ter data_pagamento.

Verificação realizada

Após a aplicação, as restrições foram testadas dentro de uma transação desfeita ao final (nenhum dado foi gravado):

Tentativa de inserçãoResultado
Serviço sem informar status (fica 'Pendente', sem data)Aceita
'Pago' com data_pagamentoAceita
'Pago' sem data_pagamentoBloqueada (chk_servico_pagamento)
'Pendente' com data_pagamentoBloqueada (chk_servico_pagamento)
Status inválido ('Talvez')Bloqueada

Regras aplicadas pelo backend (Etapa 2.2)

Além das restrições do banco, o backend valida as regras de negócio do pagamento antes de gravar:

Operação (rota)Comportamento
Cadastrar serviço
POST /servico		Aceita status e data_pagamento opcionais. Sem status, o serviço entra como 'Pendente'. Com 'Pago' e sem data, usa a data de hoje.
Marcar como pago / desfazer
PUT /servico/:id/pagamento		{"status": "Pago", "data_pagamento": "AAAA-MM-DD"} registra o recebimento (data opcional, padrão hoje). {"status": "Pendente"} desfaz e limpa a data. Responde com o status e a data gravados.
Editar serviço
PUT /servico/:id		Não altera o status de pagamento, evitando apagar um recebimento por engano. Bloqueia mudar a data do serviço para depois da data em que ele foi pago.
  • Data de pagamento futura (HTTP 400): não é possível registrar um recebimento que ainda não aconteceu.
  • Data de pagamento anterior à data do serviço (HTTP 400). Ex.: A data de pagamento não pode ser anterior à data do serviço (10/11/2026).
  • Status inválido (HTTP 400): apenas "Pago" ou "Pendente" (maiúsculas/minúsculas são ignoradas).
  • Data em formato inválido ou inexistente (HTTP 400), como 2026-02-30.
  • Serviço inexistente (HTTP 404).

Exemplo de uso: total a receber por academia

SELECT contratante,
       COUNT(*)                        AS servicos_pendentes,
       SUM(valor)                      AS total_a_receber,
       DATEDIFF(CURDATE(), MIN(data))  AS dias_do_mais_antigo
  FROM tb_registro_servico
 WHERE status = 'Pendente'
 GROUP BY contratante
 ORDER BY dias_do_mais_antigo DESC;

8. Etapa 5.1 — Dados do Prestador

Objetivo: permitir que o próprio técnico cadastre, pelo sistema, os dados que aparecem nos recibos e orçamentos enviados às academias (nome, CPF/CNPJ, contato, cidade e chave PIX), sem que essas informações fiquem fixas no código. Todos os campos são opcionais, e o técnico pode escolher não exibir seus dados nos documentos, mesmo que estejam preenchidos.

tb_prestadorNOVA

Tabela de configuração com no máximo uma linha, já que o sistema é usado por um único técnico. Foi criada separada de tb_usuario porque aquela tabela guarda credenciais de acesso (CNPJ e senha obrigatórios), enquanto estes dados são opcionais e destinados à exibição pública nos documentos.

  • id_prestador (PK) INT NOT NULL DEFAULT 1: Identificador fixo. Só pode valer 1.
  • nome VARCHAR(100) NULL: Nome do técnico ou da empresa.
  • documento VARCHAR(14) NULL: CPF (11 dígitos) ou CNPJ (14 dígitos), armazenado somente com números. A formatação (pontos, barra e traço) é aplicada na exibição.
  • telefone VARCHAR(20) NULL: Telefone ou WhatsApp, guardado como digitado.
  • email VARCHAR(100) NULL: E-mail de contato.
  • cidade VARCHAR(100) NULL: Cidade/UF de atuação.
  • chave_pix VARCHAR(100) NULL: Chave PIX para a academia efetuar o pagamento.
  • exibir_nos_documentos TINYINT(1) NOT NULL DEFAULT 1: Se 1, os dados preenchidos aparecem nos recibos e orçamentos; se 0, os documentos são gerados sem eles.
  • atualizado_em TIMESTAMP NOT NULL: Data/hora da última alteração (preenchida automaticamente pelo banco).

Restrições

  • chk_prestador_unico: id_prestador = 1, garantindo um único cadastro.
  • chk_prestador_documento: o documento, quando informado, deve ter exatamente 11 ou 14 dígitos numéricos.

Verificação realizada

Tentativa (em transação desfeita ao final)Resultado
Cadastro com todos os campos vaziosAceita (padrão: exibir nos documentos)
Segunda linha (id_prestador = 2)Bloqueada (chk_prestador_unico)
CPF com 11 dígitos / CNPJ com 14 dígitosAceitas
Documento com pontuação ou com 9 dígitosBloqueadas (chk_prestador_documento)

Regras aplicadas pelo backend

RotaComportamento
GET /prestadorDevolve os dados cadastrados. Se ainda não houver cadastro, devolve todos os campos vazios com exibir_nos_documentos = true.
PUT /prestadorCria o cadastro na primeira vez e atualiza nas seguintes (INSERT ... ON DUPLICATE KEY UPDATE). Campos vazios são gravados como nulos. O CPF/CNPJ é aceito com ou sem pontuação e gravado só com dígitos.
  • CPF/CNPJ com quantidade de dígitos diferente de 11 ou 14 (HTTP 400).
  • E-mail em formato inválido (HTTP 400).
  • Texto maior que o tamanho da coluna (HTTP 400), com o nome do campo na mensagem.

Conteúdo do arquivo backend/migrations/001_pecas_servico.sql (Etapa 1.1):

ALTER TABLE tb_item
  ADD COLUMN preco_custo DECIMAL(18,2) NULL AFTER categoria,
  ADD CONSTRAINT chk_item_preco_custo CHECK (preco_custo IS NULL OR preco_custo >= 0);

-- 2) Tabela associativa Serviço x Peça (N:N)
CREATE TABLE tb_servico_item (
  id_servico_item     INT NOT NULL AUTO_INCREMENT,
  id_registro_servico INT NOT NULL,
  id_item             INT NOT NULL,
  quantidade          INT NOT NULL,
  custo_unitario      DECIMAL(18,2) NOT NULL DEFAULT 0.00,
  PRIMARY KEY (id_servico_item),
  UNIQUE KEY uk_servico_item (id_registro_servico, id_item),
  KEY fk_si_item (id_item),
  CONSTRAINT fk_si_servico FOREIGN KEY (id_registro_servico)
    REFERENCES tb_registro_servico (id_registro_servico)
    ON DELETE CASCADE ON UPDATE CASCADE,
  CONSTRAINT fk_si_item FOREIGN KEY (id_item)
    REFERENCES tb_item (id_item)
    ON DELETE RESTRICT ON UPDATE CASCADE,
  CONSTRAINT chk_si_quantidade CHECK (quantidade > 0),
  CONSTRAINT chk_si_custo CHECK (custo_unitario >= 0)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_0900_ai_ci;

Conteúdo do arquivo backend/migrations/003_prestador.sql (Etapa 5.1):

CREATE TABLE tb_prestador (
  id_prestador          INT NOT NULL DEFAULT 1,
  nome                  VARCHAR(100) NULL,
  documento             VARCHAR(14)  NULL,   -- CPF (11) ou CNPJ (14), somente dígitos
  telefone              VARCHAR(20)  NULL,
  email                 VARCHAR(100) NULL,
  cidade                VARCHAR(100) NULL,
  chave_pix             VARCHAR(100) NULL,
  exibir_nos_documentos TINYINT(1)   NOT NULL DEFAULT 1,
  atualizado_em         TIMESTAMP    NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP,
  PRIMARY KEY (id_prestador),
  CONSTRAINT chk_prestador_unico CHECK (id_prestador = 1),
  CONSTRAINT chk_prestador_documento CHECK (
    documento IS NULL OR documento REGEXP '^([0-9]{11}|[0-9]{14})$'
  )
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_0900_ai_ci;

Como desfazer (rollback)

As reversões devem ser feitas na ordem inversa da aplicação. Reverter a Etapa 5.1 (apaga os dados do prestador):

DROP TABLE tb_prestador;

Reverter a Etapa 2.1 (perde o histórico de pagamentos):

ALTER TABLE tb_registro_servico
  DROP CHECK chk_servico_pagamento,
  DROP CHECK chk_servico_status,
  DROP COLUMN data_pagamento,
  DROP COLUMN status;

Reverter a Etapa 1.1 (apaga os registros de peças usadas em serviços):

DROP TABLE tb_servico_item;
ALTER TABLE tb_item
  DROP CHECK chk_item_preco_custo,
  DROP COLUMN preco_custo;
